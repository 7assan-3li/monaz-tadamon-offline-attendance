# مهارة المعايير الأمنية المتقدمة للتطبيقات المنفصلة (Offline Security Standards)
**مشروع نادي تضامن حضرموت | MONAZ Security Blueprint**

تم تصميم هذه المهارة لتوفير أعلى معايير الأمان الدولية (OWASP, NIST, Cryptographic RFCs) المتوافقة بدقة مع طبيعة التطبيق المحلي غير المتصل بالإنترنت:

---

## 1. معايير التشفير غير المتماثل (Asymmetric Cryptography Standards)

### أ. خوارزمية التوقيع والتحقق المعتمدة:
* **الاعتماد الصارم لـ Ed25519 (RFC 8032):**
  * استخدام منحنى `Ed25519` الرقمي بدلاً من RSA التقليدي؛ لأنه فائق السرعة، خفيف على معالجات الأجهزة اللوحية، ومقاوم لهجمات القنوات الجانبية (Side-Channel Attacks).
  * **عزل المفاتيح:**
    * المفتاح الخاص السري (`Private Key`): يُحفظ حصراً في بيئة خادم Laravel داخل متغيرات بيئة مشفرة (`.env`), وممنوع منعاً باتاً ظهوره أو تجميعه في تطبيق Flutter.
    * المفتاح العام (`Public Key`): مدمج بثبات داخل كود Flutter بصيغة آمنة للتحقق من التوقيع فقط.
* **التسلسل المعياري للبيانات (Canonical Serialization):**
  * لمنع هجمات التلاعب بترتيب الحقول في JSON عند التحقق، يجب استخدام تسلسل ترتيبي صارم للحقول (Deterministic Canonical Ordering) قبل التوقيع والتحقق.

---

## 2. معايير مكافحة التلاعب بالوقت والساعة (Anti-Clock-Tampering Engine)

### أ. محرك العلامة المائية التصاعدي الصارم (Strict Monotonic High-Watermark):
1. **المسار المزدوج للعلامة المائية (Dual-Watermark Latch):**
   * يُسجل أعلى طابع زمني (`High-Watermark`) في مكانين مستقلين:
     * في جدول الأمان الداخلي لقاعدة بيانات SQLite.
     * في مخزن مشفر محلي للنظام (`flutter_secure_storage` أو ملف نظام محمي).
2. **فحص الـ Delta الزمني والتصاعد:**
   ```dart
   // التحقق قبل أي عملية كتابة أو تحضير
   if (currentDeviceTime.isBefore(storedHighWatermark)) {
     throw ClockTamperedException("تم رصد تراجع في ساعة وتاريخ النظام!");
   }
   ```
3. **قفل التلاعب (Tamper Latch):**
   * عند اكتشاف إرجاع الساعة، يدخل التطبيق في حالة `ClockTamperedState` ويُقفل التفاعل فوراً.
   * لا يمكن فك القفل إلا بتعديل ساعة الجهاز ليتطابق أو يتجاوز أعلى وقت تم تسجيله، أو إدخال كود إعادة المزامنة الزمني من المزود.
4. **عداد النبضات التراكمي (Internal Runtime Ticks):**
   * تشغيل `Timer.periodic` لحساب دقائق التشغيل الفعلي (Active Uptime) تراكمياً دون الاعتماد المطلق على تاريخ التقويم.

## 3. معايير البصمة العتادية وربط الأجهزة (Hardware Fingerprint Binding)

1. **البصمة المركبة متعددة العوامل (Composite Multi-Factor):**
   * اشتقاق معرف الجهاز من خليط مجزأ لـ 4 مكونات عتادية صلبة:
     * معرّف المعالج (Processor ID).
     * معرّف اللوحة الأم والـ BIOS.
     * الرقم التسلسلي للقرص الصلب الأساسي (Drive Serial).
     * عنوان MAC لبطاقة الشبكة الأساسية.
2. **التجزئة مع الملح السري (Salted HMAC-SHA256):**
   * دمج هذه العناصر وتجزئتها عبر `HMAC-SHA256` باستخدام مفتاح ملح سري مخصص للمشروع لمنع التخمين أو التوليد المعاكس.
3. **الربط الإلزامي في كود التفعيل:**
   * كود التفعيل يحتوي بداخله على هاش بصمة الجهاز؛ وأي محاولة لتشغيل نفس الكود على جهاز آخر ترفضها خوارزمية التحقق محلياً 100%.

---

## 4. معايير حماية البيانات المحلية ورمز الـ PIN (Data & PIN Security)

1. **تشفير رمز الحماية (PIN Code Security):**
   * يُمنع منعاً باتاً تخزين رمز مرور الإعدادات (PIN) كنص صريح (Plain Text).
   * يجب استخدام خوارزمية التجزئة مع ملح عشوائي `PBKDF2` أو `Argon2id` أو `SHA-256 + Salt`.
   * مقارنة الرمز برمجياً يجب أن تتم بطريقة الوقت الثابت (Constant-Time Comparison) لمنع هجمات التوقيت (Timing Attacks).
2. **عزل ملف الترخيص عن النسخ الاحتياطي:**
   * عند استخراج نسخة احتياطية لكشوفات النادي لنقلها عبر USB، تُستثنى جداول الترخيص والعلامة المائية تماماً لمنع هجمات إعادة تعيين الاشتراك (Backup Replay Attack).
3. **سلامة ملفات النسخ الاحتياطي (Backup Integrity Checksum):**
   * كل ملف نسخة احتياطية يصدره التطبيق يُلحق بتجزئة تحقق `SHA-256 Checksum`؛ وعند الاستعادة يتم التحقق من سلامة الملف للتأكد من عدم تلفه أو العبث بمحتواه.

---

## 5. معايير أمان ترحيل التمارين والمزامنة دون إنترنت (Offline Sync & Dispatch Security)

1. **التوقيع الرقمي لحزمة الترحيل (Signed Dispatch Delta):**
   * عند قيام جهاز الميدان بترحيل التمرين عبر QR أو الربط المحلي، تُوقع الحزمة بـ `HMAC-SHA256` باستخدام مفتاح الاقتران المحلي المشترك (`Local Pairing Secret`) المضمن في كود تفعيل النادي.
   * لا يقبل جهاز الإدارة استيراد أي تمرين إلا بعد التحقق الرياضي من صحة التوقيع ومطابقة معرف جهاز الميدان التابع لنفس النادي.
2. **الحماية الصارمة من هجمات إعادة الإرسال والتكرار (Anti-Replay Protection):**
   * كل جلسة تحمل معرف `session_uuid` فريداً وطابعاً زمنياً.
   * يتم تخزين الجلسات المستلمة بنمط `UPSERT / Idempotent`؛ ومحاولة إعادة مسح نفس الكود يتم تجاهلها دون أي تكرار للبيانات.
3. **القفل التام غير القابل للرجعة (Immutable Dispatch Latch):**
   * يُحدث عمود `is_locked = 1` محلياً في جدول `sessions` فور الترحيل، وتُعطل واجهة المستخدم كافة أدوات التعديل في جهاز الميدان، مما يمنع التلاعب الميداني بعد مغادرة الملعب.

## 6. معايير أمان لوحة تحكم المزود (Laravel 12 Security Standards)

1. **حماية المفتاح الخاص (Private Key Vault):**
   * يُحفظ المفتاح الخاص كمتغير بيئي مشفر في بيئة الإنتاج (`LARAVEL_ED25519_PRIVATE_KEY`).
   * يُمنع كتابة المفتاح الصريح في أي ملف كود أو تتبعه عبر Git (`.gitignore`).
2. **سجل التدقيق غير القابل للتعديل (Immutable Audit Log):**
   * تسجيل كل عملية توليد ترخيص: (معرف الجهاز، اسم النادي، الباقة، هوية المستخدم الذي أصدر الكود، الطابع الزمني الدقيق).
3. **التحقق الصارم من المدخلات (Strict FormRequest Sanitization):**
   * فحص معرّف الجهاز عبر تعبير نمطي صارم (Regex: `^TD-[A-Z0-9]{4}-[A-Z0-9]{4}$`) لمنع أي محاولات حقن.
4. **حماية لوحة Filament:**
   * تفعيل حماية الهجمات المتكررة (Rate Limiting) على شاشات التوليد وتسجيل الدخول.
   * تشغيل المصادقة الثنائية (2FA) لمسؤولي الترخيص في MONAZ.

---

## 7. معايير حماية الكود المصدري أثناء البناء (Binary Hardening)

عند بناء النسخة الإنتاجية (Release Build) لتطبيق Flutter:
1. **التعتيم البرمجي (Obfuscation):**
   * بناء التطبيق دائماً بأمر التعتيم وفصل معلومات التنقيح:
     ```bash
     flutter build apk --obfuscate --split-debug-info=/<symbols-path>
     flutter build windows --obfuscate --split-debug-info=/<symbols-path>
     ```
2. **حظر أدوات التنقيح (Anti-Debugging):**
   * تعطيل رسائل الـ `print` والـ `debugPrint` في وضع الإنتاج لضمان عدم تسريب أي أثر لبصمة العتاد أو التواقيع في الـ Console.

---

## 8. قائمة التحقق الأمني الإلزامية (Security Audit Checklist):
- [ ] هل المفتاح الخاص (`Private Key`) معزول تماماً ومستحيل الوصول إليه من جهة تطبيق Flutter؟
- [ ] هل يتم التحقق من العلامة المائية الزمنية (`High-Watermark`) قبل كل عملية كتابة في قاعدة البيانات؟
- [ ] هل يدخل التطبيق في حالة `ClockTamperedState` ويقفل الواجهة فوراً عند تقديم أو تأخير ساعة الجهاز؟
- [ ] هل كود التفعيل مربوط بصمة عتادية مركبة (`Composite Hardware Hash`) يستحيل تكرارها؟
- [ ] هل رمز PIN للإعدادات مجزأ بملح عشوائي وتتم مقارنته بـ Constant-Time؟
- [ ] هل حزمة الترحيل الميدانية موقّعة بـ HMAC ومحمية من التزوير وإعادة الإرسال؟
- [ ] هل يُقفل التمرين تماماً على جهاز الميدان فور الترحيل وتُمنع أي تعديلات لاحقة؟
- [ ] هل ملف النسخة الاحتياطية معزول تماماً عن بيانات الترخيص ومحمي بـ Checksum؟
- [ ] هل تم تطبيق التعتيم البرمجي (`--obfuscate`) على التطبيق عند تجميعه؟
- [ ] هل كُتبت اختبارات آلية (`Security Tests`) للتحقق من رفض التواقيع المزورة، ورفض التلاعب بالوقت، وتطابق بصمة العتاد؟
